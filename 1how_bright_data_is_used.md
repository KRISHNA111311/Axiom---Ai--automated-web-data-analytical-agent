# Bright Data in Axiom: A Novel Integration for AI‑Driven Web Data Analysis

## 1. Introduction

Bright Data’s Scraper Studio is typically used as a standalone tool – users log into the dashboard, describe what they want to scrape, and the platform generates a scraper that can be triggered via the CLI or API.

Axiom takes this a step further. Instead of treating Bright Data as an external tool that a user operates manually, we have **embedded the entire Bright Data lifecycle** – scraper creation, estimation, execution, and self‑healing – into a fully autonomous AI agent. The user never visits the Bright Data dashboard; they simply ask a natural‑language question, and the agent orchestrates everything behind the scenes.

This document explains how Axiom uses Bright Data in a novel way, blending AI reasoning, dynamic scraper generation, and intelligent credit optimisation into a seamless pipeline.

## 2. Core Innovations

### 2.1 AI‑Driven Scraper Generation from Natural Language

**Standard usage:** A user manually writes a description of the fields they want and runs `bdata scraper create` from the terminal.

**Axiom’s approach:** The user’s question is parsed by Gemini, which extracts the analytical task (e.g., “compare price and rating”). The system then automatically constructs a precise field list (e.g., `product_title, price, rating, number_of_reviews`) and builds a description that matches Bright Data’s required format. The CLI is invoked through `npx` with **zero global installation**, and the collector ID is cached for reuse across runs.

```python
# Axiom constructs this dynamically from the user's query
description = f"Extract ONLY these fields: {fields_str}. Do not extract any other data. Preserve exact values from the webpage. Use null if a field is unavailable. Return structured JSON."
```

### 2.2 Smart Estimation: Predicting Scrape Time with Linear Regression

**Standard usage:** Users run the scraper with a fixed timeout or wait for the default polling duration.

**Axiom’s innovation:** Before the final scrape, Axiom runs a series of **sample batches** (e.g., 60s, 90s, 120s). Each sample is cancelled early via the Bright Data API, and the number of records retrieved is recorded. The system then fits a linear regression model (`records = rate × time + overhead`) to predict exactly how long the final run should take to achieve the user’s target record count. This approach:

- **Saves credits** – the final run is skipped entirely if a sample already returns enough records.
- **Adapts to site speed** – the same logic works for fast sites (books.toscrape.com) and slow, heavily protected ones (Amazon India).
- **Handles cold starts** – the first run of a scraper is often slower, so we include a warm‑up phase that discards the first one or two samples.

### 2.3 Automated Self‑Healing Without Dashboard Intervention

**Standard usage:** Bright Data offers a “Self‑Healing” button in the dashboard or a CLI command to heal a scraper.

**Axiom’s approach:** If the sandbox script fails (e.g., due to a missing import or a column name mismatch), the error is fed back to Gemini, which rewrites the script. This is **self‑healing at the analysis level**, not just at the scraper level. The pipeline retries up to `--max-retries` times, and the user never needs to open the Bright Data dashboard.

### 2.4 Process‑Tree Management for Reliable Job Cancellation

Bright Data’s CLI runs as a Node.js process that spawns child processes. A naive `process.kill()` often leaves orphans running in the background, which can consume credits unnecessarily. Axiom solves this by:

- Launching the CLI in a **new process group** (`CREATE_NEW_PROCESS_GROUP` on Windows, `os.setsid` on Linux).
- Using `taskkill /F /T` on Windows or `os.killpg` on Linux to **terminate the entire process tree**.
- Polling the output file after cancellation to ensure the JSON is fully written before reading it.

### 2.5 Seamless Integration with the Rest of the Pipeline

Bright Data is just one component in Axiom’s larger architecture. After the JSON is retrieved, it is:

1. Flattened with `pandas.json_normalize` (handling nested fields like `price.value`).
2. Mapped to a standard schema (`title`, `price`, `rating`, etc.).
3. Stored in DuckDB via a privacy broker that **never exposes raw rows** to the AI.
4. Analysed by a deterministic audit engine (skewness, variance, class imbalance).
5. Visualised with 15+ labelled charts generated by Gemini‑written code running in a Docker sandbox.

Bright Data is therefore not an isolated scraping step – it is the **data ingestion layer** of a fully automated analysis pipeline.

## 3. Technical Implementation Highlights

### 3.1 No Global Installation – Pure `npx`

Every Bright Data CLI command is run through `npx -p @brightdata/cli`, so **nothing is installed globally**. This keeps the project self‑contained and avoids version conflicts.

### 3.2 Collector Caching

The collector ID is cached locally using a hash of the URL and description. If the same URL is scraped again with the same fields, the existing collector is reused – saving the AI generation credits and time.

### 3.3 Graceful Cancellation and Output Waiting

After sending the cancel request to `https://api.brightdata.com/dca/jobs/{job_id}/cancel`, Axiom polls the output file for up to 10 seconds, waiting for valid JSON. This handles the case where the CLI is still writing the file after the cancellation signal is sent.

### 3.4 Polling with Timeout

The `_extract_job_id` method reads the CLI’s stdout in a background thread with a 30‑second timeout. This prevents the pipeline from hanging indefinitely if the CLI output is buffered or delayed.
